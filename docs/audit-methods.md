# Audit methods, stage inputs and example outputs

This reference describes collector method 1.0.0, the current practice runner and
readiness contract 2. Read `methodVersion` and `thresholds` in your own
`analysis.json` when comparing runs. Commands below assume the extracted kit's
top-level folder. The practice commands require the practice ZIP; use
`tools/gap_audit.py collect` for your own websites.

## 1. Define the source-to-target comparison

**Inputs:** approved source URLs or a source sitemap, source/target origins,
inclusions, exclusions, route mappings and acceptance criteria.

The collector deduplicates the inventory, restricts it to the source origin and
path scope, and sorts the retained URLs. URL normalization removes fragments and
retains path case, queries and trailing slashes. An exact `routeMap` entry changes
the target route; otherwise the path/query is retained on the target origin.
Local inventory paths resolve beside the configuration file.

The practice runner generates this mapping:

```json
{
  "sourceOrigin": "http://127.0.0.1:8851",
  "targetOrigin": "http://127.0.0.1:8852",
  "routeMap": {"/guide/": "/help/"},
  "documentPrefixes": ["/downloads/"]
}
```

This is an excerpt, not a complete configuration. The full practice configuration
is saved as `runs/practice-01/demo-inputs/config.json`. The four source routes
are `/`, `/resources/`, `/contact/` and `/guide/`. `/help/` is a target mapping,
not another source page. `scope.md` records journeys and acceptance criteria;
the collector does not infer them from the configuration.

**Check:** the retained inventory covers the promised scope and each moved route
has the intended target. Inventory and link limits stop collection with an error;
they do not silently choose a sample. Partial runs remain incomplete.

## 2. Collect HTTP evidence and calculate a static baseline

```bash
python3 practice/run_demo.py start --out runs/practice-01
```

The runner serves only the two fixture trees on loopback addresses. It generates
temporary configuration/inventory inputs, calls the real collector, copies those
inputs and the exercise scope into the new run, and leaves the servers running.

The collector requests each source/target page, records status, redirect chain,
final URL, content type and capture time, and preserves response bodies. It parses
static HTML without executing JavaScript. Text, heading, link-label and image-alt
signals use `<main>` when present; otherwise extraction falls back to the whole
document and flags the missing main region. Script, style, noscript and template
text are ignored. CSS visibility is not evaluated.

Unique same-origin destinations from the extracted **target content links** are
checked separately. Already collected target responses are reused. Other
destination checks use HTTP GET without reading the body. This does not crawl
every navigation link, validate a document's identity or verify JavaScript actions.
Shared navigation and document contents therefore need browser review.

For real-site collection, defaults are 1,000 pages, 10,000 unique checked links,
100 sitemap documents, a 20-second request timeout and a 0.2-second request
delay. The practice configuration explicitly uses 10/30/5 limits, a five-second
timeout and zero delay for its local fixtures. Page bodies and expanded sitemap
inputs have a 10 MiB limit. Redirects must stay on the configured origins; a
blocked redirect remains unverified. Check these settings against the approved
scope rather than increasing them to hide an incomplete run.

**Produces:**

```text
runs/practice-01/
  evidence.json           configuration, inventory and captured observations
  snapshots/              raw response bodies and inventory inputs
  analysis.json           calculated metrics, flags, totals and evidence binding
  reviews.json            empty finding register bound to this evidence
  report.md               generated human-readable static baseline
  demo-inputs/config.json exact local configuration generated by the runner
  demo-inputs/urls.txt    exact four-route source list
  scope.md                copied practice requirements
```

Snapshot filenames contain the raw-content SHA-256. Identical bodies can share a
snapshot; the number of snapshot files is not a page count. The practice input
copies and scope are runner outputs, rather than outputs of every direct
`gap_audit.py collect` invocation.

**Check:** the original exercise has four comparable pairs, one unique unavailable
target and two affected pages. The initial confirmed finding count is zero.
The terminal remains open because it is serving the sample sites, not because
collection is still pending.

## 3. Interpret the measurements

### Text similarity

The collector case-folds text, extracts Python `\w+` tokens longer than two
characters, and counts their frequency. For source and target frequency vectors
`A` and `B`, it calculates:

```text
textSimilarity = sum(A[token] * B[token])
                 / (sqrt(sum(A[token]^2)) * sqrt(sum(B[token]^2)))
```

Values are rounded to six decimal places. An empty token vector produces `null`.
The comparison ignores word order, so reordered text can retain a high score.
It does not measure layout or successful interactions.

Illustrative calculation: `alpha alpha beta` has frequencies `(2, 1)` and
`alpha beta` has `(1, 1)`. Their score is `3 / sqrt(10) = 0.948683`.
This arithmetic example is not a practice-site finding.

### Heading and link-label coverage

Whitespace-normalized, case-folded **distinct source labels** form the denominator:

```text
coverage = count(distinct source labels also present on target)
           / count(distinct nonempty source labels)
```

Heading coverage uses heading text; link-label coverage uses extracted anchor
text. Repeating a label does not increase retained distinct-label coverage.
An empty source set produces `null`, rather than an automatic pass. Heading order,
heading level and link destinations require their separate checks.

The original resources row contains these selected fields:

```json
{
  "route": "/resources/",
  "content": "Review",
  "metrics": {
    "textSimilarity": 0.860689,
    "headingCoverage": 0.5,
    "linkTextCoverage": 1.0
  }
}
```

Two distinct source headings become one retained target heading: coverage is
`1 / 2`. The download's label is retained even though its destination fails.
Contact has `textSimilarity: 1.0` and `linkTextCoverage: null` because its text is
retained and it has no extracted main-content links; its mobile layout still fails.

### Flags, availability and denominators

- Text similarity below 0.90, heading coverage below 0.90 or link-label coverage
  below 0.95 triggers content review. Missing H1, title differences, redirects and
  main-region fallback can also require review. Additional metadata/accessibility
  flags are recorded separately from the content classification.
- A usable page needs a successful 2xx response, no fetch error and parsed HTML.
  A successful status alone is insufficient for a comparable HTML pair.
- A destination is unavailable for 404/410. Errors, access failures and other
  unsuccessful statuses remain unverified. A 2xx availability result does not
  establish correct document content.
- `unavailableLinks` counts unique failed target URLs. `affectedPages` counts
  inventoried pages linking to at least one such URL. `textSampleSize` counts
  non-null text scores used by the mean. Use each field's own denominator.

## 4. Prepare blank review records

```bash
python3 practice/run_demo.py prepare-review --run runs/practice-01
```

**Reads:** existing `evidence.json`, `analysis.json` and bundled review templates.
It checks the collection binding, normalizing platform line endings in memory,
then seeds the blank manifest with that run's evidence reference.

**Produces:** `browser/`, `browser-review.json` and `audit-checklist.md` when absent.
Existing records are kept unchanged. A conflicting evidence reference is an error;
the command does not substitute a new hash into an old review.

The following is a structural example; the bracketed value is explanatory text:

```json
{
  "schemaVersion": 1,
  "evidenceSha256": "[copied from this run's analysis.json]",
  "checks": [],
  "components": [],
  "screenshotPairs": [],
  "limitations": ["Browser review has not yet been performed."]
}
```

**Check:** arrays remain empty until observations are recorded. `Created:` and
`Kept existing:` messages describe file setup; they are not passing audit results.
Neither `start` nor `prepare-review` creates `readiness.json` or performs browser
checks.

## 5. Record browser observations and findings

**Inputs:** scope, static review candidates, page IDs, source/target pages and
the required states/viewports. Match browser/version, dimensions, session, scroll
position and interaction state. Perform mouse and keyboard actions independently.

**Produces:** screenshot originals, a populated browser manifest and checklist,
and supported findings in `reviews.json`. Record actions, expected and observed
results, reviewer/time, capture metadata and evidence references. Preserve each
original image and hash before defining a crop in original-image pixels.

These records have different jobs:

| Record | Decision it supports |
|---|---|
| `browser-review.json` | What was checked, at which states/viewports, and what happened |
| `reviews.json` | Which observed differences require action, their impact/priority and acceptance tests |
| `readiness.json` | Page/block/variant/use counts, retained capabilities and remaining work after review |

The checklist uses Pass, Fail, Unverified or Not applicable with a reason.
Browser-manifest checks use `pass`, `fail` or `unverified`; exclusions belong in
`limitations`. P0/P1/P2 describe impact under the scope's criteria, while
Good/Review/Critical/Unverified describe content fidelity. They are separate axes.

## 6. Render the measured report from saved evidence

```bash
python3 tools/gap_audit.py render --evidence runs/practice-01/evidence.json --reviews runs/practice-01/reviews.json --out runs/practice-01
```

The renderer validates the evidence/review relationship, recalculates static
measurements, incorporates supported findings, and replaces `analysis.json` and
`report.md`. It makes no new HTTP requests. With `--reviews` supplied, it does not
rewrite the finding register, original evidence, snapshots or screenshots.

**Check:** `evidenceSha256` stays tied to the same capture. `reviewsSha256`
identifies the canonicalized finding register. Confirmed findings can increase from zero
to three while static response/availability counts remain unchanged. Repeat with
the same evidence, reviews, arguments and toolkit to reproduce the measured
output; use a new collection when testing changed sites. Both JSON references
hash parsed records serialized with the collector's canonical JSON method, not
arbitrary on-disk whitespace. Screenshot and PDF hashes instead use raw bytes.

### What the different hashes identify

| Identifier | Method and purpose |
|---|---|
| `PAGE-…` | First 12 hex characters of SHA-256 of the full source URL. Ports, queries and route spelling can change IDs. |
| `analysis.evidenceSha256` | SHA-256 of the collector's canonical JSON serialization: sorted keys, two-space indentation, Unicode retained, trailing LF, encoded as UTF-8. Use the stored value, especially across Windows CRLF file I/O. |
| Snapshot/capture SHA-256 | Raw HTTP-body, inventory-input or original image bytes. A crop does not change the retained original or its hash. |
| PDF/build-record hashes | Identify assessment, records, renderer, dependencies/fonts and output used for a particular build. They do not prove that the underlying observations are correct. |

## 7. Assess readiness, build and verify the PDF

A reviewer prepares `readiness.json` from the actual page/block/variant/use census
and recorded checks. Visual similarity, functional completeness and readiness are
separate fields. Complete requires all stated required states verified. Ready
requires Close visuals, Complete applicable behavior (or Not applicable), verified
required states/viewports, completed applicable quality checks and no open
limitations. Parent ratings must also respect their scoped component and exact
variant ratings. A passed text comparison cannot supply these judgments.

Run validation, build and verification as distinct steps:

| Command/stage | Reads and checks | Produces |
|---|---|---|
| `build_readiness_pdf.py --validate-only` | Assessment structure, page/type/variant counts, references, rating gates and screenshot hashes/crops | Validation counts on stdout; no PDF |
| `build_readiness_pdf.py --out …` | Validated assessment, screenshots, supplied records, fonts and pinned packages | Readiness PDF and `.build.json`; supplied records embedded byte for byte |
| `verify_pdf.py --assessment … --out …` | PDF/build/assessment integrity, references, embedded originals and rendered-page count | `text.txt`, `checks.json` and page PNGs under the chosen QA folder |
| Visual inspection | Every rendered page, screenshot crop, table and chart | Recorded inspection and repairs where needed; rendering alone leaves inspection pending |

Use the full commands in `docs/reproduce-audit.md` or the practice walkthrough.
Missing-assessment errors mean the review input is absent, not that the builder
should invent it. The global readiness chart counts distinct body block types;
page bars count uses. Preserve these units and all unverified limits.

## 8. Retest repairs and preserve the comparison

Collect the repaired copy into a new run, prepare its blank review records, and
repeat the original acceptance tests plus affected shared components/journeys.
Record fixed, still-open, new and unverified outcomes with fresh evidence.

**Produces:** a new evidence set, review records and assessment/report for the new
state. A separate retest record links stable finding IDs to the original and new
evidence. Original findings and their original bindings remain unchanged. If URLs
or ports changed, map page IDs explicitly by logical route.

**Check:** the repaired practice copy has zero unavailable target URLs, restored
resources context and a fitting mobile panel. Verify the browser results and
document identity before recording closure. Rebuilding an old report only checks
reproduction of that saved state.
